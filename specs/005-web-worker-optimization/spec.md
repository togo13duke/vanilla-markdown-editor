# Feature Specification: Web Worker + パフォーマンス最適化

**Feature Branch**: `005-web-worker-optimization`
**Created**: 2025-12-30
**Status**: Draft
**Input**: User description: "Sprint 5: Web Worker + パフォーマンス最適化 - Markdownパースをワーカーへ移管し、長文でも入力が止まらない構造にする"

## User Scenarios & Testing

### User Story 1 - 長文入力時のスムーズな編集体験 (Priority: P1)

ユーザーが5,000文字以上の長文Markdownを編集する際に、入力遅延を感じることなくスムーズにタイピングできる。メインスレッドでのパース処理がなくなり、キー入力への応答が即座に行われる。

**Why this priority**: エディタの基本価値である「入力の滑らかさ」を担保する最重要機能。長文でもストレスなく執筆できることがこのスプリントの中核目標。

**Independent Test**: 5,000文字以上のMarkdownを入力し、連続タイピング時にカクつきや遅延がないことを体感で確認できる。

**Acceptance Scenarios**:

1. **Given** 5,000文字以上のMarkdownが入力されている状態, **When** ユーザーが連続してタイピングする, **Then** キー入力に対する応答が遅延なく行われる（体感的にスムーズ）
2. **Given** 10,000文字以上のMarkdownがある状態, **When** ユーザーが文章を編集する, **Then** 入力カーソルがフリーズすることなく追従する
3. **Given** 複雑なMarkdown（見出し・コードブロック・リンク多数）がある状態, **When** ユーザーが編集を続ける, **Then** メインスレッドがブロックされず入力が継続できる

---

### User Story 2 - プレビューの非同期更新 (Priority: P1)

編集中にプレビューがバックグラウンドで更新され、入力操作を妨げない。パース結果が返ってきたタイミングでプレビューが反映されるが、その間も入力は継続できる。

**Why this priority**: 入力とプレビュー更新が独立して動作することで、ユーザーは途切れない執筆体験を得られる。US1と同等に重要。

**Independent Test**: 長文入力中にプレビューが段階的に更新され、入力操作がブロックされないことを確認できる。

**Acceptance Scenarios**:

1. **Given** Workerでパース処理中の状態, **When** ユーザーが入力を続ける, **Then** 入力がブロックされずプレビューは後から更新される
2. **Given** 連続して入力が行われている状態, **When** 複数のパース要求が発生する, **Then** 最新の結果のみがプレビューに反映される（古い結果は破棄）
3. **Given** パース処理が完了した状態, **When** 結果がWorkerから返却される, **Then** プレビューエリアが最新のHTMLで更新される

---

### User Story 3 - 開発時のデバッグ支援（メインスレッドフォールバック） (Priority: P2)

開発者がWorkerの問題をデバッグしやすいよう、メインスレッド版のパース処理を残し、切替可能にする。本番ではWorkerを使用し、開発時は必要に応じてメインスレッドに切り替えられる。

**Why this priority**: Worker導入によるデバッグ難化を防ぐ補助機能。P1機能の品質担保に貢献する。

**Independent Test**: コンソールまたは設定でメインスレッド/Worker版を切り替え、両方で動作確認できる。

**Acceptance Scenarios**:

1. **Given** アプリケーションが起動している状態, **When** デフォルト設定で動作する, **Then** Worker版のパース処理が使用される
2. **Given** デバッグフラグが有効な状態, **When** アプリケーションが動作する, **Then** メインスレッド版のパース処理が使用される
3. **Given** メインスレッド版で動作している状態, **When** Markdownを入力する, **Then** プレビューが正常に更新される（Worker版と同じ結果）

---

### User Story 4 - 古いパース結果の破棄（requestIdパターン） (Priority: P1)

連続入力時に複数のパース要求が発生しても、最新の結果のみがプレビューに反映される。古いrequestIdを持つ結果は無視され、ちらつきや巻き戻りが発生しない。

**Why this priority**: 高速入力時のUX品質を担保する必須機能。結果の巻き戻りは致命的なUX劣化につながる。

**Independent Test**: 高速タイピング時にプレビューがちらつかず、常に最新の内容が表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ユーザーが高速で連続入力している状態, **When** 複数のパース結果が返却される, **Then** 最新のrequestIdを持つ結果のみが適用される
2. **Given** 古いパース結果が先に返却された状態, **When** その後に新しいパース結果が返却される, **Then** 古い結果は無視され新しい結果のみが表示される
3. **Given** パース要求が送信された状態, **When** 新しい入力により新たなパース要求が発生する, **Then** 新しいrequestIdが付与された要求が送信される

---

### User Story 5 - パフォーマンスメトリクス（任意） (Priority: P3)

開発者がパース処理のパフォーマンスを把握できるよう、パース時間をコンソールに出力する。これにより最適化の効果を測定できる。

**Why this priority**: 任意機能。パフォーマンス改善の効果測定に役立つが、ユーザー体験には直接影響しない。

**Independent Test**: 開発者ツールのコンソールでパース時間を確認できる。

**Acceptance Scenarios**:

1. **Given** Workerでパース処理が完了した状態, **When** 結果が返却される, **Then** パース時間（ミリ秒）がコンソールに出力される
2. **Given** メトリクス出力が有効な状態, **When** 複数回パースが実行される, **Then** 各パースの処理時間が個別に記録される

---

### Edge Cases

- Workerの初期化に失敗した場合はどうなるか？ → メインスレッドにフォールバックし、エディタは継続動作する
- 非常に大きなファイル（50,000文字以上）ではどうなるか？ → パース時間は増加するが、メインスレッドはブロックされずUI応答性は維持される
- ブラウザがWeb Workerをサポートしない場合はどうなるか？ → メインスレッド版で動作する（低機能フォールバック）
- 連続入力中にWorkerがクラッシュした場合はどうなるか？ → エラーをキャッチし、メインスレッド版にフォールバックする

## Requirements

### Functional Requirements

- **FR-001**: システムはMarkdownパース処理をWeb Workerで実行しなければならない
- **FR-002**: システムはメインスレッドをブロックせずにプレビューを更新しなければならない
- **FR-003**: システムはパース要求にrequestIdを付与し、古い結果を破棄しなければならない
- **FR-004**: システムはWorker失敗時にメインスレッド版にフォールバックしなければならない
- **FR-005**: システムは開発時にメインスレッド/Worker版を切り替え可能にしなければならない
- **FR-006**: Workerからの応答にはパース結果（HTML）とrequestIdが含まれなければならない
- **FR-007**: システムは最新のrequestIdを管理し、古い結果を無視しなければならない
- **FR-008**: システムはWorker初期化失敗時にエラー通知を表示し、フォールバックしなければならない

### Key Entities

- **ParseRequest**: パース要求を表す（text: パース対象テキスト, requestId: 一意識別子）
- **ParseResult**: パース結果を表す（html: 変換後HTML, requestId: 対応する要求ID, metrics: オプションのパフォーマンス情報）
- **WorkerState**: Workerの状態を管理（initialized: 初期化済みか, currentRequestId: 最新のrequestId）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 5,000文字以上のMarkdownを編集時に、ユーザーが入力遅延を体感しない
- **SC-002**: 10,000文字以上のMarkdownでも、連続タイピング中にUIがフリーズしない
- **SC-003**: 高速入力時にプレビューのちらつきや巻き戻りが発生しない
- **SC-004**: Worker失敗時も、エディタ機能が継続して使用可能である
- **SC-005**: プレビュー更新は入力操作と独立して非同期で行われる

## Assumptions

- 対象ブラウザはWeb Workerをサポートしている（モダンブラウザ）
- 既存のmarkdownService.jsのパース処理をWorkerに移植可能である
- デバウンス機能は既存のpreviewService.jsに実装済みである
- IndexedDBへの保存処理は別タイマー（autosaveService.js）で管理されている
